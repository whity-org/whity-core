# Security readiness: pen test and ISO 27001

Status: **Phase 1 audit done 2026-11-22.** Phase 2 fixes are tracked in the [fix plan](#7-fix-plan-phase-2) below.
Owner: WHIT-1335.

Whity and its services will get an outside penetration test and an ISO/IEC 27001:2022 audit. This page lists every gap we found against:

- **OWASP ASVS 4.0.3, Level 2**, and
- **ISO/IEC 27001:2022 Annex A, technological controls (A.8.1 to A.8.34)**,

across the four repositories that hold Whity's own code, so that neither the pen test nor the audit turns up something that needs a security rewrite. Each gap has the file or setting, a severity, the fix and an estimate, and says whether it is **code**, a **repo setting** (only the owner changes those) or **process** (policies, records, evidence).

Related: [Threat model](../wiki/Threat-Model.md) (refreshed in the same change) · [Pen-test scoping brief](../wiki/Pen-Test-Scoping-Brief.md) · [Tenant isolation](../wiki/TENANT_ISOLATION.md) · [Backups and restore](../wiki/Backups-and-Restore.md) · [Go-live checklist](../wiki/Go-Live-Checklist.md).

## 1. Scope and method

| Repository | Commit audited | What it is |
| --- | --- | --- |
| whity-org/whity-core | `2a7247613` (develop) | Core API (PHP 8.4, FrankenPHP), web app (Next.js), render service, plugin SDK, CLI |
| whity-org/whity-id | `b83f27f` (main) | Whity ID: OIDC provider and OAuth 2.1 server (Laravel) |
| whity-org/whity-plugins | `d35318c` (main) | First-party plugins (Whity Pay, plugin store, appointments, themes, templates) |
| whity-org/whity-builder | `3eebbdf` (main) | Whity Builder (Laravel) and its MCP toolset |

Not in scope: whity-web (marketing sites), whity-agent (desktop), whity-builder-connector, the live server and its `.env`, Cloudflare settings, GitHub organisation settings. Findings that depend on those are marked **to verify**.

Method: source review of every repository at the commits above, read-only `gh api` calls for alerts and repository settings, and a local image build plus Trivy scan for the base-image question. No test ran against a shared or live database. About 80 security issues fixed in the November lanes (identity confinement, token epochs and refresh-family revocation, the role grant guard, MCP grants, SSRF, chat leaks) were rechecked only where they touch a gap below.

### Severity

| Severity | Meaning here |
| --- | --- |
| Critical | Exploitable from the internet now, cross-tenant or full takeover. Fix before anything else. |
| High | A pen tester or auditor will report it as a major finding, or it removes a control that other controls rely on. Fixed (or owner-decided) before the pen test. |
| Medium | A normal ASVS L2 or A.8 finding. Fix before the audit or record a risk acceptance. |
| Low | Defence in depth, hygiene, or only reachable with access we already trust. |
| Info | Recorded for the auditor; no change needed or a product decision. |

## 2. Summary

**No Critical gaps.** Ten High gaps, of which four are code and six need the owner (a repo setting, a signing key or a product decision).

| Repository | Critical | High | Medium | Low | Info |
| --- | --- | --- | --- | --- | --- |
| whity-core (CE, CO, TM) | 0 | 7 | 37 | 32 | 2 |
| whity-id (WID) | 0 | 0 | 10 | 10 | 3 |
| whity-plugins (WP) | 0 | 0 | 2 | 4 | 2 |
| whity-builder (WB) | 0 | 1 | 6 | 9 | 2 |
| GitHub settings (RS) | 0 | 2 | 1 | 0 | 0 |

CO-30 (no required review) is counted under whity-core and also listed with the repository settings.

The architecture holds up: tenant isolation has a CI guard, a table-classification test and a route probe that attacks every route; tokens are short-lived, epoch-bound and revocable; OAuth in Whity ID follows the current security BCP; payment webhooks are signed and never trust amounts from the payload. **None of the gaps needs a rewrite.** The two largest pieces of work are the central field validator (#2174, about 110 handlers, done in batches) and a runtime sandbox for code plugins (an architecture item we accept as a documented risk once package signing is live).

#### Checked and fine (evidence)

- **Short access token and server-side revocation.** Access tokens last 15 min (`src/Auth/AuthHandler.php:1002`). Every non-public request checks the token's session is still live (revoked jti, token epoch) (`public/index.php:1471`; `src/Auth/TokenValidator.php`).
- **Refresh rotation with reuse detection.** Reusing a refresh token revokes the whole family (`src/Auth/AuthHandler.php:2320`; `src/Auth/SessionService.php:108-224`).
- **Cookie flags.** `HttpOnly; SameSite=Lax` always, and `Secure` whenever `APP_ENV` isn't `development` (production is the default) (`src/Auth/CookieManager.php:23`, `:40-45`).
- **CSRF.** Any state-changing request that carries an auth cookie needs `X-Requested-With`, and the login/refresh/logout/select/switch/SSO-workspace POSTs always do (`src/Http/Middleware/CsrfGuard.php`).
- **JWT handling.** HS256 is pinned and `exp`, `jti` and `type` are required (`src/Auth/JwtParser.php:52-80`). The secret must be at least 32 characters in production (`src/Auth/JwtSecretGuard.php:18`, `:36-42`). The TOTP key has a dev fallback only when `APP_ENV=development` (`src/Auth/TotpService.php:81-93`).
- **Password change.** It needs the current password, bumps `token_epoch`, revokes the current tokens and sends a security email (`src/Auth/AuthHandler.php:1690-1696`, `:1776-1852`). Accounts backed by an identity provider are refused clearly (`:1676-1682`).
- **Login brute force.** Throttled per IP (20), per profile (10) and per email (10) over 15 min, checked before the database lookup. Login errors all return "Invalid credentials" (`src/Auth/LoginThrottleService.php:21-23`; `src/Auth/AuthHandler.php:303-430`).
- **TOTP.** ±1 step window, with a per-profile step floor that blocks replay (`src/Auth/TotpService.php:169-220`; `src/Auth/TotpStepFloor.php`). 2FA disable and regenerate are throttled (`src/Api/TwoFactorHandler.php:288`, `:475`). An admin can enforce 2FA through a policy (`src/Auth/TwoFactorPolicyResolver.php`).
- **Backup codes.** 15 codes of 12 random characters (`random_int`), stored as bcrypt hashes and single use (`src/Auth/BackupCodesService.php:42-74`).
- **Reset and verification links.** Reset links last 1 h and email verification links 24 h (`src/Core/Identity/PasswordResetService.php:53`; `src/Core/Identity/EmailVerificationService.php:34`). The forgot-password step is limited per email and per IP and doesn't reveal whether an account exists (`src/Api/PasswordResetHandler.php:87-103`).
- **Backend API headers.** `default-src 'none'; frame-ancestors 'none'`, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`, and HSTS for 1 year with includeSubDomains outside development (`src/Http/SecurityHeaders.php:73-100`). A handler's own CSP is always forced into a sandbox (`:120-170`). The 500 and OPTIONS responses carry the same headers (`public/index.php:7546`, `:7578`).
- **Frontend headers (other than CSP).** `X-Frame-Options: DENY`, `nosniff`, `no-referrer`, and HSTS outside development (`web/next.config.ts:91-106`).
- **CORS.** Exact-match origin allow-list from env, credentials only for allow-listed origins, and `Vary: Origin` (`src/Http/Cors.php`). Website CORS (plans, contact) sends no credentials (`src/Http/WebsiteCors.php`).
- **Error responses.** The top-level catch returns a generic 500 with a reference ID and logs the trace on the server only (`public/index.php:7571-7598`). The Next proxy returns a generic 502-style body (`web/app/api/[...path]/route.ts:168-176`). I checked 28 places where handlers use `getMessage()`: all go to logs except `PasswordPolicy`'s fixed message (`src/Auth/AuthHandler.php:1772`), which is safe.
- **PHP hardening.** `expose_php=Off` and `session.upload_progress.enabled=0` (`Dockerfile:86-89`). The release image ships without composer or git (`Dockerfile:95+`).
- **Request bodies.** Capped at 1 MiB, content type and JSON object checked before CSRF, tenant or RBAC run (`src/Http/Middleware/RequestBodyValidator.php:69`).
- **Upload type checks.** File types are sniffed from the bytes and a mismatch with the declared type is refused. Form uploads are capped at 10 MiB, public ones at 5 MiB (`src/Core/Form/FormUploadPolicy.php`). DOCX files are inspected with entry-count, size and `..` checks (`src/Core/Form/WordDocumentInspector.php:105-142`).
- **Zip handling.** Plugin zips are guarded against zip-slip and zip bombs (entries, per-entry size, total size, compression ratio) (`src/Core/PluginInstaller.php:42-58`, `:545+`). The XLSX reader refuses DOCTYPE (no XXE) and caps entry size (`src/Core/Contacts/Import/SpreadsheetReader.php:284-300`).
- **SVG.** SVG is allowed only for logos, goes through an allow-list sanitizer, and is served with its own CSP and `nosniff` (`src/Core/Branding/BrandingAssetValidator.php:29-64`; `src/Api/BrandingApiHandler.php:99-106`). Form banners refuse SVG (`src/Api/FormBannerApiHandler.php:21-22`).
- **Served files.** Download filenames are sanitized (`src/Api/FormSubmissionsApiHandler.php:608-617`; `src/Api/DocumentSourcesApiHandler.php:787`; `src/Api/ChatApiHandler.php:561`). Files are stored outside the webroot (`public/index.php:3546`, `STORAGE_ROOT`, default `/app/storage`). Stored files are served `private` with `nosniff`.
- **Webhooks.** Signatures are verified (`src/Api/ExternalBillingApiHandler.php:333`, `:655`; `src/Api/PaymentWebhookApiHandler.php:31`).
- **Client IP headers at the proxy.** The Next proxy strips client-supplied IP headers and sets the internal one itself (`web/app/api/[...path]/route.ts:57-72`). The remaining risk is CE-4.
- **Auth tokens in the browser.** The web app keeps no tokens in `localStorage`. The only `dangerouslySetInnerHTML` uses are three static bootstrap scripts.

##### whity-builder: checked and fine

- **Connector HMAC**: SHA-256 HMAC with a 256-bit per-connection secret (`ConnectorSignature.php:25-28`), compared with `hash_equals` (`:50`), 300 s window both directions (`:44`), nonce format checked (`:47`), nonce recorded atomically under a `(connection_id, nonce)` primary key so a racing replay loses (`:54-59`, `database/migrations/2026_11_01_000004_add_connector_secret.php:22-28`); signature checked before nonce insert.
- **Tenant binding of connector calls**: the secret is per connection; drafts are always looked up with `where('connection_id', $connection->id)` (`app/Mcp/BuilderTools.php:277`, `:260`); actions in the workspace go through core `/mcp` with that connection's token where core re-checks RBAC and turns publish/rollback into proposals (`app/Core/CoreClient.php:147-160`, refuses to publish if core cannot make proposals).
- **Key rotation/revocation**: signed `POST /connector/rotate` and `/connector/revoke` exist and work without the builder UI; reconnecting mints a new secret.
- **Secrets at rest**: `token`, `refresh_token`, `connector_secret` use Laravel `encrypted` casts and `$hidden` (`app/Models/Connection.php:145-157`); secret page sent with `Cache-Control: no-store` (`ConnectController.php:89-91`); Blade uses escaped `{{ }}` only, no `{!! !!}` anywhere.
- **OAuth flow**: PKCE S256, `state` compared with `hash_equals` and pulled from session (single use), `iss` checked, code exchanged server-side with client secret, `aud` must equal the requested resource, issuer metadata must name the same issuer (`ConnectController.php:52-72`, `app/Access/WhityId.php:31-49,123-135`). Refresh under a row lock so the rotating refresh chain is not burned (`app/Access/ConnectionTokens.php`).
